# game19《BANG!》桌面演出层迁移

## 迁移目标

1. 让单体攻击、决斗、多人攻击明确表现行动者和目标。
2. 让“行动前摇—玩家响应—服务器结算”三个阶段在视觉上连续可辨。
3. 通过移动牌标、判定、生命变化、装备和出局揭晓增强物件实体感。
4. 通过当前玩家、响应玩家、行动来源和濒死玩家的持续状态增强玩家存在感。
5. 动画只解释服务器已经接受的结果，不参与规则推进或倒计时。

## 信息边界

- 公开事件可以包含：已公开使用的牌、行动者、目标、公开判定牌、生命变化和已经揭晓的身份。
- 私人事件可以包含：自己摸到或取得的具体牌。
- 公共事件不得包含：未公开身份、手牌牌值、随机抽取到的秘密牌、尚未结算的私人选择。
- 旁观者只接收公开事件；私人事件只合并进对应玩家的裁剪视图。

## 本阶段事件范围

- 开局、回合交接、摸牌和角色摸牌能力。
- 【砰！】、【闪！】、木桶判定、受伤与濒死。
- 决斗往返、加特林和印第安人的逐玩家响应。
- 啤酒救援、酒馆、装备、监狱与炸药判定。
- 抢劫、拆除、杂货店、超额弃牌、出局和阵营胜利。
- 巴特受伤摸牌、苏茜空手摸牌、格林戈反抢、秃鹫山姆接收遗牌、击杀歹徒奖励和警长误杀副警长惩罚。

## 验收标准

- [x] 事件由服务器分配全局递增序号并随房间持久化。
- [x] 公开事件在正式玩家和旁观视图中一致。
- [x] 摸牌和隐藏牌转移详情只发送给有权知道的玩家。
- [x] 攻击、响应、决斗、伤害和救援具有可辨认的方向与中央播报。
- [x] 多人攻击按服务器实际响应顺序进入事件队列。
- [x] 首次加入和断线重连不会重播历史事件。
- [x] 动画不会禁用操作按钮，也不会延长服务器截止时间。
- [x] 手机端使用实际玩家列表位置计算轨迹。
- [x] `prefers-reduced-motion` 下仍保留文字结果并取消主要运动。
- [x] 旧SQLite快照缺少演出字段时可以自动恢复。
- [ ] 完成真实联机验收：砰/闪、决斗、群体攻击、濒死救援、出局和胜负。

## 第二阶段：演出队列防积压

## 本阶段目标

- 同一次服务端操作生成的公有事件和逐玩家私有事件使用同一个 `sceneId`，客户端只播放一个聚合场景。
- 快速操作造成积压时自动缩短演出，不让画面长期落后于权威状态。
- 伤害、濒死、救援、出局和胜负等关键结算优先保留。
- 私人摸牌、抢牌和遗牌内容继续只发送给有权看到的玩家。

## 事件优先级

- 1：轮次开始、普通摸牌等高频状态。
- 2：私人摸牌、装备、弃牌、杂货店选牌等普通操作。
- 3：攻击、响应、防御、决斗、判定、抢拆与治疗。
- 4：开局、伤害、濒死、救援、出局、警长惩罚和比赛结果。

## 客户端节奏

- 正常播放：1450ms。
- 队列达到 2 个待播场景：650ms 追赶。
- 队列达到 5 个待播场景：330ms 严重积压模式。
- 新到达的 4 级紧急场景会清除尚未播放的低优先级旧场景，但不会中断正在播放的当前场景。

## 验收重点

1. 连续出牌和快速响应后，演出应在短时间内追上当前游戏状态。
2. 一次【砰！】应作为一个“攻击并等待响应”场景展示，而不是两段长期排队。
3. 受伤、濒死、救援、出局以及胜负不能被普通摸牌动画淹没。
4. 抢牌或私人摸牌的具体牌名只能由相关玩家看到，旁观者和无关玩家不得看到。
5. 重连不重播历史演出；SQLite 恢复后新场景编号继续递增。
